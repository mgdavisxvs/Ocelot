# Ocelot Operator Manual

Complete operational reference for the Go rewrite of the Gazelle BitTorrent tracker. Covers configuration, HTTP API, database schema, peer mechanics, and economic settlement.

Go 1.26 SQLite WAL BEP 3 / BEP 23 ComputeCommons

# Overview

Ocelot is a private BitTorrent tracker serving Gazelle-compatible sites. It handles peer announces, scrapes, admin updates, and optional economic credit settlement via ComputeCommons.

Startup

The binary reads its config via the -c flag (default: ocelot.conf). On first run it creates the SQLite database in db_dir. The tracker listens on listen_port over raw TCP — not stdlib net/http.

IPv4 Only

Compact peer format (BEP 23) encodes 4-byte IPv4 + 2-byte port. IPv6 addresses pass initial validation but produce a nil IPPort and are excluded from peer lists with a warning.

Process Signals

SIGUSR1
Merge-reload — reloads torrents, users, whitelist, and tokens from the database without wiping in-memory peer lists.
SIGTERM
Graceful shutdown — flushes pending DB writes, checkpoints WAL, closes all shards.
SIGHUP
Config hot-reload — re-parses ocelot.conf, applies mutable fields without restart.
SIGINT
Same as SIGTERM. Drains active connections with a 30-second timeout.

# Signals

SignalEffect
SIGINTGraceful shutdown: stop accepting, drain connections (30 s), close DB.
SIGTERMSame as SIGINT.
SIGHUPHot-reload config: re-parse ocelot.conf, apply mutable fields in-place.
SIGUSR1Merge-reload: update torrent metadata, user permissions, whitelist from DB. Does not wipe peer lists.

SIGHUP — hot-reload fields

Updated without restart: site_password, report_password, numwant_limit, announce_interval, peers_timeout.

Require restart: listen_port, max_middlemen, db_dir, gazelle_url, keepalive_timeout, reap_peers_interval.

kill -HUP $(pgrep ocelot)

# Routes

All routes on a single TCP port (listen_port). Client routes use the user's 32-char passkey; admin routes use site_password.

GET/{passkey}/announceBEP-3 announce
GET/{passkey}/scrapeBEP-48 scrape
POST/{sitepass}/updateAdmin mutations (dispatched by ?action=)
GET/{sitepass}/statsRuntime statistics (JSON)
GET/{sitepass}/torrentsIn-memory torrent list (JSON)
GET/{sitepass}/peersPeer list for one torrent (JSON)
GET/{sitepass}/whitelistCurrent client whitelist (JSON)

# Announce

Standard BEP-3 announce. Responses use compact format (BEP-23): each peer is 6 bytes (4-byte IP + 2-byte port).

Required parameters

ParameterDescription
info_hash20-byte raw info hash (URL-encoded)
peer_id20-byte peer ID. First 4–8 bytes matched against whitelist.
portClient's listening port (1–65535)
uploadedTotal bytes uploaded this session
downloadedTotal bytes downloaded this session
leftBytes remaining. 0 = seeder.

Optional parameters

ParameterDefaultDescription
event—started, stopped, completed
numwant25Peers requested. Capped at numwant_limit.
corrupt0Corrupt bytes reported
Passkey URL

Passkeys must be exactly 32 characters: http://tracker.example.com:34000/{32-char-passkey}/announce

# Scrape

BEP-48 scrape. Returns seeder, leecher, and completed counts for up to 50 torrents per request.

GET /{passkey}/scrape?info_hash=<hash1>&info_hash=<hash2>

Response is bencoded: d5:filesd20:<hash>d8:completei14e10:downloadedi891e10:incompletei3eeee

If no info_hash parameters are supplied, the tracker returns scrape data for all known torrents (capped at numwant_limit).

# Database

SQLite shard files named ocelot-YYYY-MM.db, stored in db_dir. A new shard is created when the current one reaches 84 GB. Historical shards remain open for aggregate reads.

data/db/
├── ocelot-2025-01.db   ← historical (read-only)
├── ocelot-2025-06.db   ← historical
└── ocelot-2026-09.db   ← current (all writes)

Startup sequence

1. Parse -c flag → locate config file
2. ParseConfigFile() → load key=value pairs
3. NewSQLiteShardManager(db_dir)
      → open all monthly .db files
      → apply WAL pragmas
      → CREATE TABLE IF NOT EXISTS (8 tables)
4. Loader.LoadAll() → TorrentList, UserList, Whitelist, Tokens
5. Select SiteComm: GazelleSiteComm or NoOpSiteComm
6. Reaper.Start()    → evict stale peers
7. Scheduler.Start() → WAL checkpoint loop
8. Server.ListenAndServe()
9. Block on SIGINT/SIGTERM

# SQLite Pragmas

Applied on every shard open:

PRAGMA journal_mode = WAL;
PRAGMA synchronous  = NORMAL;
PRAGMA busy_timeout = 5000;

The Scheduler goroutine runs PRAGMA wal_checkpoint(TRUNCATE) every schedule_interval seconds. If the WAL grows large after a crash, truncate it while the tracker is stopped:

sqlite3 data/db/ocelot-$(date +%Y-%m).db "PRAGMA wal_checkpoint(TRUNCATE);"

Manual inspection

# Top 10 torrents by seeders
SELECT id, seeders, leechers, snatched FROM torrents ORDER BY seeders DESC LIMIT 10;

# Active peers for a torrent
SELECT user_id, ip, remaining, datetime(last_announce,'unixepoch')
FROM peers WHERE torrent_id = 42 AND active = 1;

# Reload

After Gazelle updates the database (new torrents, banned users, token grants), send SIGUSR1 to merge changes without restarting:

kill -USR1 $(pgrep ocelot)
# or via systemd:
kill -USR1 $(systemctl show -p MainPID ocelot | cut -d= -f2)

For config-only changes (passwords, intervals), use SIGHUP:

kill -HUP $(pgrep ocelot)
# or:
systemctl reload ocelot

# FreeType Values

ValueNameEffect
0NormalUpload and download both counted toward ratio.
1FreeDownload not counted; upload still counted.
2NeutralNeither upload nor download counted.

Per-user tokens

A token grants one user freeleech on one torrent, overriding the torrent's FreeType. Token lifecycle:

Gazelle grants token → inserts into tokens table → SIGUSR1
User announces with Left > 0 and a download delta:
  tracker detects token → sets downloadedChange = 0
  → calls DB.RecordToken() → sets expireToken = true
On completion → SiteComm.ExpireToken(torrentID, userID)
Gazelle receives callback → marks token consumed

If gazelle_url is unset, ExpireToken is a no-op (logged only).

# Procedures

Add torrent at runtime

curl "${TRACKER}/${SITE_PASS}/update?action=add_torrent&id=42&info_hash=${INFO_HASH}&free_type=0"
# {"status":"ok","message":"torrent added"}

Ban a user

curl "${TRACKER}/${SITE_PASS}/update?action=remove_user&passkey=abc123...abc123"

Their next announce returns Passkey not found. Active peers remain until reaped.

Rotate site password after incident

  1. Edit ocelot.conf: change site_password
  2. kill -HUP $(pgrep ocelot) — takes effect immediately
  3. Update in Gazelle's tracker settings

Graceful restart (zero-peer-loss window)

  1. Wait for low-traffic window (e.g. 03:00 local)
  2. systemctl stop ocelot — drains connections (30 s)
  3. Replace the binary
  4. systemctl start ocelot — Loader.LoadAll() restores torrent/user data
  5. Peers re-announce within one interval (default 30 min) and rebuild swarms

Systemd unit

[Unit]
Description=Ocelot BitTorrent Tracker
After=network.target

[Service]
Type=simple
User=ocelot
WorkingDirectory=/opt/ocelot
ExecStart=/opt/ocelot/ocelot -c /etc/ocelot/ocelot.conf
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target

# Troubleshooting

"unregistered torrent"

Info hash is not in TorrentList. Either: never added via add_torrent; tracker restarted and torrent_hashes is empty; or info_hash encoding differs. Fix: add_torrent or SIGUSR1 after populating DB.

"your client is not on the whitelist"

Peer ID prefix not in whitelist. Fix: add_whitelist for the prefix, or empty the whitelist to allow all clients.

"access denied, leeching forbidden"

User's can_leech = 0. Fix: re-add user with can_leech=1 or update user_passkeys directly and send SIGUSR1.

High announce failure rate

  1. Whitelist too restrictive — peers using unapproved clients
  2. Torrents not registered — Gazelle/tracker sync lag
  3. Users not registered — passkey mismatch
  4. Client does not support BEP-23 compact format (rare)

"no space left on device"

Free disk or expand the filesystem. To archive old shards:

systemctl stop ocelot
gzip -9 data/db/ocelot-2025-01.db
systemctl start ocelot
Warning

The tracker will not open compressed files; historical queries for that shard return zero.

Peers not appearing after restart

Peer state is RAM-only. After a restart, peers re-announce within one interval (default 30 min) and swarms rebuild naturally.

# Security

Change defaults immediately

Default passwords are 32 zeros. Any host with network access can call admin routes. Change site_password and report_password before exposing the port to any network.

Firewall

Admin routes and client announces share the same port. Restrict admin access via a reverse proxy or internal firewall — there is no port-level distinction between client and admin traffic.

IP protection

Users with protect_ip = 1 have their IP omitted from the peers table. The IP is still used in-memory for compact peer list construction but is never written to disk.

Peer ID whitelist

Run with a non-empty whitelist to restrict to known BitTorrent clients and block automated scrapers:

-qB4   qBittorrent 4.x
-qB5   qBittorrent 5.x
-DE13  Deluge 1.3
-DE20  Deluge 2.0
-TR3   Transmission 3.x
-TR4   Transmission 4.x
-lt    libtorrent (various)

Reverse proxy considerations

  • X-Forwarded-For must be set correctly — the tracker uses it for peer IP
  • Proxy must pass raw binary info_hash values without re-encoding
  • proxy_pass should target the raw TCP port
