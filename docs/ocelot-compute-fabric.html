Ocelot as a Compute Fabric

Deploy Ocelot's BitTorrent swarm as a peer-to-peer job-distribution layer — routing compute payloads, container layers, CI artifacts, ML model shards, and GPU inference tasks across heterogeneous hardware without a central broker.

Dell R640 R730 + 2×V100 16 GB M1 Mac Mini 8 GB UC-9 Compute Shuttle Prometheus + DCGM

What "Compute Fabric" Means

Ocelot's announce engine tracks which peers hold which torrent pieces in real time. When you register a payload under category = compute or category = edgeai, the swarm becomes a self-balancing distribution mesh:

  • UC-9 Compute Shuttle — GET /compute/scale returns a scale_up verdict when the leecher/seeder ratio exceeds 4, so your orchestrator knows when to spin extra workers or GPU nodes.
  • UC-2 Model Registry — ML model weights and shards are registered under category = edgeai; V100 workers pull only the diff on each version update, cutting re-distribution time from hours to minutes.
  • UC-11 Container Layer Cache — CUDA container image layers are content-addressed torrents; peers pull only missing diffs, eliminating registry bottlenecks when deploying GPU workloads across a cluster.
  • UC-18 CI Artifact Store — build artefacts (binaries, test reports, ONNX exports) are registered with a TTL; Ocelot garbage-collects them after ci_artifact_ttl seconds.
  • UC-20 Edge Rollout — staged rollouts advance automatically when the anomaly rate stays below rollout_anomaly_gate, giving you zero-downtime GPU firmware and driver updates with built-in canary gating.
R730 + V100 role in the fabric

The R730 acts as a GPU seeder: it seeds model weights and CUDA container layers at 10 GbE line rate while simultaneously running inference. Because BitTorrent is upload-parallel, a single V100 node can distribute a 14 GB model to 20 workers in the time a unicast copy would reach 2. Both V100s contribute independently — each worker in the swarm picks pieces from whichever GPU node responds fastest.

Private tracker precondition

All peers must present a valid passkey. Run Ocelot behind a firewall; set a strong site_password and jwt_secret before exposing the Admin API. The compute fabric is only as secure as your passkey issuance process.

# ── UC: Live / streaming ──────────────────────────────────────────

# ── UC: Data retention ────────────────────────────────────────────

backup_retention_days = 45

Tuning note: The R730 Xeon E5-2600 v4 CPUs handle fewer simultaneous goroutines efficiently than the R640's Xeon Gold. If you see high CPU steal or softirq time under load, reduce max_connections to 1000 and max_middlemen to 80000. Ocelot's hot path is announce processing; it does not use the GPU at all.

GPU Workload Pipeline (R730 + V100)

The R730 plays two concurrent roles: seeder (distributing model weights via the swarm) and inference worker (consuming those weights on its V100s). This section covers the end-to-end setup.

Step 1 — Register a model torrent (category = edgeai)

Create a torrent file from your model weights directory, then register it with category = edgeai so Ocelot's per-category middleware applies. 

# Create a torrent (using any BT client or mktorrent)
mktorrent -l 24 -n llama3-8b-q4 \
  -a http://YOUR_R730_IP:6969/PASSKEY/announce \
  /data/models/llama3-8b-q4/

# Register via Admin API
curl -s -X POST http://localhost:8181/admin/torrent/add \
  -H "Authorization: Bearer $OCELOT_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "info_hash":  "TORRENT_INFO_HASH_HEX",
    "category":   "edgeai",
    "name":       "llama3-8b-q4",
    "ttl_seconds": 0
  }'
Step 2 — Set up GPU worker passkeys 
# Create a user per GPU worker node (or per GPU, for per-GPU accounting)
curl -s -X POST http://localhost:8181/admin/user/add \
  -H "Authorization: Bearer $OCELOT_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"username":"gpu-worker-01","can_leech":true,"can_seed":true}'

# Response includes passkey:
# {"passkey": "a1b2c3d4e5f6..."}

# Workers announce to:
# http://YOUR_TRACKER:6969/a1b2c3d4e5f6/announce?info_hash=...&event=started&...
Step 3 — Pull weights on GPU worker (aria2c example) 
# On each GPU worker node — pull model weights via the swarm
# aria2c supports BitTorrent natively
aria2c \
  --seed-ratio=2.0 \
  --seed-time=0 \
  --dir=/data/models \
  model.torrent

# After download, load into V100 VRAM via vLLM
vllm serve /data/models/llama3-8b-q4 \
  --tensor-parallel-size 2 \   # span both V100s (NVLink or PCIe peer-to-peer)
  --max-model-len 8192 \
  --port 8000
Step 4 — Scale-out with /compute/scale 
# Orchestrator poll loop (bash example; use your own scheduler in prod)
while true; do
  RESP=$(curl -s http://localhost:8181/compute/scale \
    -H "Authorization: Bearer $OCELOT_TOKEN")

  SCALE_UP=$(echo "$RESP" | jq -r '.scale_up')
  RATIO=$(echo "$RESP" | jq -r '.ratio')

  echo "$(date) ratio=$RATIO scale_up=$SCALE_UP"

  if [ "$SCALE_UP" = "true" ]; then
    # Launch an additional GPU worker via your preferred method:
    # - Kubernetes: kubectl scale deployment gpu-worker --replicas=+1
    # - Nomad:      nomad job scale gpu-inference +1
    # - Raw SSH:    ssh gpu-worker-0N "systemctl start inference-worker"
    echo "Scaling up — ratio $RATIO exceeds threshold"
  fi

  sleep 30
done
Step 5 — GPU container distribution (nvidia-container-toolkit)

Register CUDA container image layers as torrents under category = container. Workers pull only the changed layers on each image update, cutting pull time from minutes to seconds for large CUDA images. 

# Export container layers as a torrent (example with docker save)
docker save nvcr.io/nvidia/pytorch:24.01-py3 | \
  gzip > pytorch-24.01.tar.gz
mktorrent -n pytorch-24.01 -a http://TRACKER:6969/PASSKEY/announce pytorch-24.01.tar.gz

# Register as container category
curl -s -X POST http://localhost:8181/container/layer \
  -H "Authorization: Bearer $OCELOT_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "info_hash":      "TORRENT_HEX",
    "image_ref":      "nvcr.io/nvidia/pytorch:24.01-py3",
    "layer_digest":   "sha256:abc123..."
  }'

# Workers pull and load:
aria2c --dir=/tmp pytorch-24.01.torrent
docker load < /tmp/pytorch-24.01.tar.gz
docker run --gpus all nvcr.io/nvidia/pytorch:24.01-py3 python -c "import torch; print(torch.cuda.is_available())"

Compute Fabric API

All Admin API calls require Authorization: Bearer <JWT>.

POST /admin/token Issue a JWT 
curl -s -X POST http://localhost:8181/admin/token \
  -H 'Content-Type: application/json' \
  -d '{"secret":"YOUR_JWT_SECRET"}' | jq .

export OCELOT_TOKEN="eyJ..."
GET /compute/scale UC-9: Scale-up verdict

Returns scale_up: true when leecher/seeder ratio > 4.0. On the R730 this maps directly to "spin another GPU worker." 

curl -s http://localhost:8181/compute/scale \
  -H "Authorization: Bearer $OCELOT_TOKEN"

# High demand
{"scale_up": true,  "ratio": 6.2, "seeders": 12, "leechers": 74}

# Adequate supply
{"scale_up": false, "ratio": 1.8, "seeders": 44, "leechers": 80}
GET /compute/eta UC-9: Job completion estimate 
curl -s "http://localhost:8181/compute/eta?info_hash=TORRENT_HEX" \
  -H "Authorization: Bearer $OCELOT_TOKEN"

{"info_hash":"abc123...","eta_seconds":42,"pieces_remaining":17,"active_peers":8}

curl -s -X POST http://localhost:8181/ci/artifact/register \
